## 0. 先理解三件事

1. **一条 `(server, workspace)` 一条连接。** 不是一条订阅一条连接。所有会话、所有规则读同一个 workspace 时共用同一条 SSE；上送的服务端过滤条件是这些规则的**并集**（`runtime.ts:356` `desiredChannels`，`connection.ts:257` `streamUrl`）。所以：新增一条更宽的规则会**重建**连接（并从当前时刻起算，不回放旧游标，`runtime.ts:400-429`）。
2. **服务端粗过滤 + 客户端精确匹配，两段分工固定。**
   - `filter:` → 服务端参数（`types` / `entityTypes`），**只能写服务端认得的维度**；
   - `match:` → 客户端对**归一化信封**逐字段比对（`match.ts`），状态、`changedFields`、操作人都只在这一段。
   - 推论：`filter` 写不了的维度（比如 `state`）**不是被忽略，而是被拒**（`config.ts:208-212`）；把状态塞进 `filter` 得到的不会是"少叫几次"，是一整条规则不可用。
3. **`action` 二选一，两个都执行。**
   - `wake`：往那个会话注入一条 prompt，让它**跑一轮**（`delivery.ts` `startRpcSession` + `session.send`）；会话正在跑一轮时**不插话**，批次进 `pendingBatch`，这一轮结束后投**一次**（`runtime.ts` `parkBatch` / `attemptDrain`）。
   - `notify`：只出未读徽标 + 系统通知，**不注入、不烧 token**（`runtime.ts` `deliverNotification`）。它在状态里的 `health` 是 `active`，未读计数在 `/api/events/subscriptions` 的 `unread` 与会话行的小圆点上。

由此得到最重要的推论：**订阅的能力上限 = 信封里有的字段**（`match.ts:6-32` 的 `EventDescriptor`）。信封里没有 key、没有 actor 的 sessionId、没有字段值，所以按 key 匹配、按"是谁改的"过滤都做不到——这类判断只能写进注入的 prompt，交给模型（`config.ts:261-262` 就是这么提示的）。

## 2. 文件放在哪、什么时候生效

按 cwd 依次查找，**用第一个存在的**（`config.ts:127` `EVENTS_CONFIG_RELATIVE_PATHS`）：

```text
.pi/events.yaml      ← 标准位置
.pi/events.yml
events.yaml
events.yml
```

- 文件不存在不是错误：`exists: false`、`sessions: []`，没有任何订阅（`config.ts:428-431`）。
- 读取失败 / YAML 解析失败 / 根节点不是对象 / `version` 不是 1 / 没有 `sessions` 数组 → **文件级错误**，整个文件的订阅都不生效（`config.ts:435-458`）。
- 单条规则有问题 → **只坏那一条**，同会话的其它规则、其它会话的规则照常工作（`config.ts:419`）。

生效时机（都是自动的，不需要重启）：

| 触发 | 效果 |
| :--- | :--- |
| 应用启动后约 2 秒 | 事件运行时才开始（`runtime.ts:614`，启动纪律见 `SSR-000097`【运行时归属】） |
| 每 15 秒一次扫描 | 重新读每个项目根下的 `events.yaml`（`runtime.ts:609`） |
| 改了 `filter` 里的 `events` / `entityTypes` | 并集变了 → 该 channel **重建连接**，游标**从当前时刻起算**（`runtime.ts:400-429`；重建不回放旧事件） |
| 改了 `match` / `inject` / `coalesceSec` | 只影响客户端，下一次命中即按新配置走 |
| 侧栏角标的细节 | 每 60 秒拉一次 `/api/events/subscriptions`（`SessionSidebar.tsx:1380-1394`） |

两条容易踩的前提：

- **项目必须在"最近项目"里。** 运行时只扫描最近会话对应的项目根（`runtime.ts:314-321` `visibleProjects` → `getRecentProjects`），一个很久没打开、没有近期会话的项目不会被扫描——不会报错，就是"安静"。
- **`server` 必须是 `mcp.json` 里 `url` 以 `/entity/mcp` 结尾的 HTTP 条目。** 名字解析失败（`runtime.ts:447-451`）或 URL 不是 entity 端点（`runtime.ts:453-454`）时**根本不会建连接**，规则显示 `paused`、原因「事件连接尚未建立（或该 server 不可用）」。

## 3. 字段速查

```yaml
version: 1                  # 顶层，只能 1
sessions:                   # 顶层，数组，一个会话一项（sessionId 唯一）
  - sessionId: "<会话 id>"
    title: "显示名"          # 可选
    subscriptions:
      - name: "规则名"            # 必填，会话内唯一（忽略大小写），不能含 #
        server: entity-base       # 必填，mcp.json 条目名
        workspace: ws_entity_base # 必填
        action: wake              # 可选，wake（默认）| notify（M2，写了会 paused）
        filter:                   # 可选，服务端粗过滤
          events: [entity.transitioned]
          entityTypes: [TASK]
          operator: alice
          linkTypes: [assigned_to]
          custom: true
        match:                    # 可选，客户端精确匹配
          eventType: [entity.transitioned]
          aggregateType: [TASK]
          from: [IN_PROGRESS]
          to: [BLOCKED, FINISHED]
          changedFields: [state]
          operator: [alice]
        coalesceSec: 30           # 可选，正整数，默认 30
        maxPerHour: 20            # 可选，正整数，默认 20 —— 滚动一小时，超了 skipped:limited
        recheck: false            # 可选，布尔，默认 false —— 投递前按 aggregateId 重读
        selfQuietSec: 15          # 可选，≥0 的整数，默认 15；0 = 关闭
        loopWindowSec: 300        # 可选，正整数，默认 300（同 aggregate 的窗口）
        loopMaxHits: 3            # 可选，正整数，默认 3（窗口内允许投递次数）
        inject: |                 # 可选，模板；省略用内置模板
          {{count}} 条变化（{{window}}s 内合批）：
          {{events}}
```

**订阅级未知键会被拒，而不是被读成"没写"。** `parseSubscription` 用 `SUBSCRIPTION_KEYS` / `SESSION_KEYS` / `ROOT_KEYS` 逐键白名单（`config.ts` `rejectUnknownKeys`）：写 `selfQuiet: 15`（少个 `Sec`）、`coalesce_sec: 5`、`max_per_hour: 5` 都会得到一条指名道姓的错误。M1 时代这些是静默忽略——校验通过、字段消失、防线不存在，这是本套配置最危险的失败模式。

## 4. `filter`：只写服务端认得的维度

```ts
// config.ts:37
export const FILTER_KEYS = ["events", "entityTypes", "operator", "linkTypes", "custom"] as const;
```

| 键 | 可写什么 | 实际用途（M1） |
| :--- | :--- | :--- |
| `events` | 事件类型名，字符串或数组（`entity.transitioned` …） | **会发给服务端**，作为同 channel 所有规则的并集（`connection.ts:265`） |
| `entityTypes` | 实体类型名，字符串或数组 | **会发给服务端**（`connection.ts:266`） |
| `operator` | 非空字符串 | 只解析进对象，M1 **不发给服务端**（`connection.ts:257-268` 只拼 `types` / `entityTypes`）。要按人过滤，写进 `match.operator` |
| `linkTypes` | 字符串或数组 | 同上，M1 不发送 |
| `custom` | 布尔 | 同上，M1 不发送 |

**`state` 不在这里，写了会被拒而不是被忽略** —— 服务端按状态过滤会被静默忽略，那样规则"看起来配好了"却永远不命中，这正是这套配置要避免的失败模式：

```text
sessionId=01a1c87d-... error=filter.state：服务端不支持按状态过滤（会被静默忽略），请把状态写进 match；订阅 #1 "状态过滤"：filter.state：服务端不支持按状态过滤（会被静默忽略），请把状态写进 match
  订阅 #1 "状态过滤" → 拒绝 filter.state：服务端不支持按状态过滤（会被静默忽略），请把状态写进 match
可用规则数: 0
```

出处：`config.ts:203-214`（`readFilter` 的未知键分支，`state` 有专门文案）。没有 `state` 这个特判之外的键，一律是 `filter.<key>：filter 只接受 events / entityTypes / operator / linkTypes / custom`。

其余拒绝分支：

| 写法 | 报错（出处 `config.ts`） |
| :--- | :--- |
| `filter: "entity.transitioned"` | `filter 必须是对象（...）`（192-196） |
| `filter.events: 5` | `filter.events 只能是数组（写的是 5）`（173-177） |
| `filter.events: [""]` | `filter.events 的每一项都必须是字符串（写的是 ""）`（178-183） |
| `filter.operator: ""` / `123` | `filter.operator 必须是非空字符串（写的是 ...）`（225-229） |
| `filter.custom: "true"` | `filter.custom 只能是 true 或 false（写的是 "true"）`（232-237） |

`filter` 全空是合法的，含义是"这个 workspace 的事件全要"，由 `match` 挡。`events` 里的 `"*"` 会原样上送（服务端支持 `entity.*` / `*`，见 `SSR-000097`【基座现状】；本仓代码不校验其语义）。

## 5. `match`：只认归一化信封

```ts
// config.ts:47
export const MATCH_KEYS = ["eventType", "aggregateType", "from", "to", "changedFields", "operator"] as const;
```

每个键的值是**谓词**：字符串、数组或 `"*"`（`config.ts:143-166` `readPredicate`）：

- `["*"]` = 任意，**包括空值**；不写 = 任意；
- 具体列表 = 值必须**命中其中之一**；事件侧的值是 `null` 时**不命中**具体列表（"转到 BLOCKED"不会因为一个没有状态的事件而触发，`match.ts:105-110`）；
- `changedFields` 是"至少命中一个"（列表对列表，`match.ts:113-118`）。

| 键 | 来自信封哪里（`match.ts:52-97` `normalizeEnvelope`） |
| :--- | :--- |
| `eventType` | `envelope.eventType` |
| `aggregateType` | `envelope.aggregateType`（实体类型名） |
| `from` | `entity.transitioned` → `payload.fromState`；`entity.created` → `null`（创建没有前态）；其它事件 → `null` |
| `to` | `entity.transitioned` → `payload.toState`；`entity.created` → `payload.state`；其它 → `null` |
| `changedFields` | `payload.changedFields`（字符串数组） |
| `operator` | `envelope.operator`（用户名） |

两条边界，写到就会被拒：

- **`match.key` 不行。** 信封里只有 `aggregateId`，没有 key：`match.key：事件信封里只有 aggregateId，没有 key；请用 recheck 或让模型去读`（`config.ts:259-264`）。顺带一句实话：`recheck` 在 M1 也不执行（第 7 节），所以现实答案是"让模型去读"。
- **`match.aggregateId` 也不行。** `MATCH_KEYS` 里没有它——能按"哪类实体"匹配，不能按"哪一条实体"匹配。要盯某一条，写进 prompt 让模型自己筛。
- 任何别的键：`match.<key>：match 只接受 eventType / aggregateType / from / to / changedFields / operator`（`config.ts:263`）。

## 6. `inject`：模板与占位符白名单

```ts
// config.ts:50
export const INJECT_PLACEHOLDERS = [
  "count", "window", "events", "aggregateType", "aggregateId", "workspaceId",
  "timestamp", "operator", "from", "to", "hitCount",
] as const;
```

| 占位符 | 值（`inject-text.ts:76-92` `renderInjection`） |
| :--- | :--- |
| `{{count}}` | 本批事件总数（同实体合并后仍按原始条数累计） |
| `{{window}}` | 窗口实际长度（秒，四舍五入） |
| `{{events}}` | 事件清单，**最多 10 条**，多出的是 `… 还有 N 条`（`inject-text.ts:21` `MAX_LISTED_HITS`） |
| `{{aggregateType}}` / `{{aggregateId}}` / `{{from}}` / `{{to}}` / `{{operator}}` / `{{timestamp}}` / `{{hitCount}}` | 批次里**最后进入**的那个聚合（不是按时间排序；`from`/`to` 为空时给空串） |
| `{{workspaceId}}` | 同上，缺失时回落到订阅的 `workspace` |

**未声明的占位符被拒，不会渲染成空串**（`config.ts:337-342`，`findUnknownPlaceholders` 在 `config.ts:276-284`）。实跑一个把 `count` / `window` 拼错的反例：

```text
  订阅 #1 "占位符写错" → 拒绝 inject 里的占位符 {{cnt}}、{{windows}} 未声明；可用：{{count}} {{window}} {{events}} {{aggregateType}} {{aggregateId}} {{workspaceId}} {{timestamp}} {{operator}} {{from}} {{to}} {{hitCount}}
可用规则数: 0
```

模板省略（或省略整个 `inject`）时用内置模板（`inject-text.ts:23-28` `DEFAULT_INJECT_TEMPLATE`）：

```text
{{count}} 条变化（{{window}}s 内合批）：
{{events}}
这不是断言：先重读这些实体的当前状态，再决定下一轮怎么派。
```

两条固定规则，**模板改不掉**：

1. 注入文本的**第一行永远是** `[事件] <sessionId>#<name>`。一个会话可能被多条规则、也可能被人同时叫醒，首行是唯一能说清"这次是谁叫的"的地方（`inject-text.ts:95-97`）。
2. 清单必须有事件行，光有计数没法判断该派什么。

同一个聚合在一次窗口内连转两次只留一行，带「合并 N 次」，且 `from`/`to` 取**最新**事件（`batch.ts:117-128`）——早先的 `from` 描述的是实体已经离开的状态。

## 7. 闸门：合批 → 复核 → 限流 → 保险丝 → 忙闲

一个批次（不是一条事件）走完这条流水线，**顺序是设计而不是实现细节**：先把同一实体的一阵抖动合起来，再做判断，否则一次抖动会被算成好几次（`lib/events/gate.ts` 顶部的注释）。

| 步骤 | 键 | 行为 | 被拒时记账 |
| :--- | :--- | :--- | :--- |
| ④ 合批 | `coalesceSec` | 从**第一条命中**起算的**固定窗口**（不随新事件顺延）：同聚合合并 `hitCount`，不同聚合进同一批，窗口结束投一次 | — |
| ⑥ 复核 | `recheck` | 投递前按 `aggregateId` 逐个 `get` 重读；实体已不存在、搬到别的 workspace、类型或 `to` 状态不再命中 → 丢掉这条；全丢则不投递 | `skipped:stale：重读后已不满足 match（<aggregateId>）` |
| ⑤ 静默期 | `selfQuietSec`（默认 15，`0` 关闭） | 距本规则上次投递不足 N 秒 | `skipped:self：距上次投递不足 15s（还剩 Ns）` |
| ⑤ 小时配额 | `maxPerHour`（默认 20） | **滚动**一小时；合批后的批次只记一次 | `skipped:limited：一小时内已投递 20 次（maxPerHour）`，健康态 `limited` |
| ⑤ 循环保险丝 | `loopWindowSec` / `loopMaxHits`（默认 300s / 3 次） | 同一个 `aggregateId` 在窗口内已投 N 次 | `skipped:loop：<aggregateId> 在 300s 内已投递 N 次（上限 3）` |
| ⑤ 风暴保险丝 | `stormWindowSec` / `stormMaxDeliveries`（会话级，默认 600s / 6 次） | 整个会话在窗口内的投递数达到阈值 | 达到阈值的那一批**先投**，然后**暂停本会话全部订阅**并弹通知；之后每条记 `skipped:paused：…` |
| ⑦ 忙闲 | — | 会话正在跑一轮：`wake` 批次进 `pendingBatch`，本轮结束后**投一次**，内容含期间全部事件；`notify` 不打断，立即提醒 | 不记账（尚未投递），`pendingCount` 可见 |
| ⑦ 投递 | `action` | `wake` 注入一条 prompt；`notify` 加未读 + 系统通知 | 成功记 `delivered` |

两条容易被忽略的事实：

- **复核读的是"现在"，不是信封。** 通道只上送 `level=envelope`，`from`/`to` 描述的是发生过什么；`recheck` 会把命中的聚合按 id 重读一次（同一个 `mcp.json` 条目，8s 超时）。读失败**不投递**，记 `skipped:recheck-failed：…` —— 注入一个无法确认的状态正是复核要防的事。
- **风暴暂停不会自动恢复。** 暂停写在 `~/.pi/agent/subscriptions/<sessionId>.json` 的 `session.paused`，重启也不清除。清掉：停掉应用、把那个字段删掉（或删掉整个文件，会同时丢掉计数与已处理游标）、重启。M2 没有面板上的"恢复"按钮，这是有意的——先让它停，再让人决定。

关于"事件不是事实"：

- 通道只上送 `level=envelope`，**信封里没有字段值**；`from`/`to` 是变动描述，不是当前状态。
- 所以内置模板和默认提示都要求模型**回读**再决策；`recheck: true` 让运行时自己先做一次同样的回读，但**不能取代模型的重读**（它只判断"还命中不命中"，不判断"这件事重不重要"）。
- 批内合并也遵循这条：同聚合取最新 `from`/`to`，`hitCount` 告诉模型"它在窗口里动过几次"。

## 8. 健康态与角标

两个来源，同一个判定函数：

- `/api/agent/running` 追加 `subscribedSessionIds` + `subscriptionHealth`（**只给结论**，`app/api/agent/running/route.ts:18-27`）；
- `/api/events/subscriptions?cwd=` 给每条规则的 `health` + `reason` + 最近唤醒 / 今日次数 / 连接态（`route.ts:70-113`），侧栏角标的 tooltip 用它。

| 健康态 | 什么时候 | 怎么解 |
| :--- | :--- | :--- |
| `active` | 连接在连/已连上（`connecting` / `active`），且没有阻塞理由 | 正常，不用管 |
| `paused` | ① **风暴保险丝**停了这个会话（`session.paused`，`runtime.ts` `ruleRuntimeStatus` 里优先判定）；② 另一个应用实例接管了这条 channel（`superseded`）；③ 连接压根没建起来：`server` 解析失败 / URL 不是 entity 端点 / 运行时还没启动 | ① 按第 7 节"风暴暂停不会自动恢复"清掉；② 关掉另一个实例（同一 `cid` 只允许一条连接，互踢是刻意的：否则两边无限对踢）；③ 核对 `mcp.json` 的条目名与 URL，别用 stdio |
| `limited` | 本规则的滚动一小时配额用完了（`maxPerHour`）。连接是好的，预算没了；`reason` 会写「一小时内已投递 N 次（maxPerHour: X）」，`hourlyCount` 是分子 | 等窗口滑过去（不需要操作），或调大 `maxPerHour`；想少叫几次应该收 `match`，不是把配额调大 |
| `unavailable` | ① `sessionId` 在磁盘上不存在（`runtime.ts:700`、`runtime.ts:727`）；② 连接态是 `auth_failed`（凭据失效）/ `reconnecting`（退避重连中）/ `unavailable` / `idle`（`runtime.ts:704-709`） | ① 修 `sessionId`（订阅不建会话）；② 401/403 不重试，要修 `mcp.json` 的凭据；重连是 1s→2s→4s…最多 60s（`connection.ts:166-170`），不用手动干预 |

会话整体健康度是各规则的合并（`runtime.ts` `sessionSubscriptionHealth`）：任一 `paused` → `paused`；否则任一 `unavailable` → `unavailable`；否则任一 `limited` → `limited`；否则 `active`。侧栏行上是铃铛 + 规则条数，`health !== "active"` 转警示样式并给原因（`lib/event-badges.ts:118-120`、`SessionSidebar.tsx:2550-2600`）。折叠项目下也有一个带计数的 chip，组内有异常时变警示色。

`notify` 规则的未读计数单独出现在同一响应的 `unread` / `lastNotifyAt` / `lastNotifyText`（会话级），并在 `/api/agent/running` 的 `subscriptionNotifications` 里推送：侧栏把「未读增量」变成和后台完成一样的未读圆点，桌面端同时弹一条系统通知（`notifyDesktop`）。打开会话（`GET /api/sessions/<id>`）才算读过，计数清零。

链路真的断了要照实说：`gap` 帧意味着"这段时间的事件确实没叫醒你"（`connection.ts`），只有 `ready` 会清零退避计数。**没有轮询兜底**——通道不可用就是不可用。

## 10. 三个最常见的配错

### ① `state` 写进 `filter`

```yaml
filter:
  events: [entity.transitioned]
  state: [BLOCKED]      # ✗
```

规则整条不可用（不是"少叫几次"），原始输出：

```text
  订阅 #1 "状态过滤" → 拒绝 filter.state：服务端不支持按状态过滤（会被静默忽略），请把状态写进 match
可用规则数: 0
```

改成 `match: { to: [BLOCKED] }`。理由：服务端过滤维度里没有状态（`SSR-000097`【基座现状】），客户端才有 `payload.toState`。

### ② 占位符名字写错

```yaml
inject: |
  {{cnt}} 条变化（{{windows}}s 内）    # ✗
```

原始输出：

```text
  订阅 #1 "占位符写错" → 拒绝 inject 里的占位符 {{cnt}}、{{windows}} 未声明；可用：{{count}} {{window}} {{events}} {{aggregateType}} {{aggregateId}} {{workspaceId}} {{timestamp}} {{operator}} {{from}} {{to}} {{hitCount}}
可用规则数: 0
```

为什么是拒绝而不是渲染成空串：`0 条变化` 读起来像事实，而真相是模板错了（`config.ts:275` 的注释即此意）。

### ③ 以为拼错的键会报错（M1 会，M2 会拒）

```yaml
subscriptions:
  - name: "带自激保险丝"
    selfQuiet: 15          # ✗ 少了 Sec
    loopMaxHits: 2
```

原始输出（`/api/events/subscriptions?cwd=` 的 `error` 原文，M2）：

```text
订阅级 selfQuiet：未知配置项（只接受 name / server / workspace / action / filter / match /
inject / coalesceSec / maxPerHour / recheck / selfQuietSec / loopWindowSec / loopMaxHits）
```

M1 时代同样的文件会**通过**：字段被静默丢掉，规则照跑，`selfQuiet` 那道防线不存在。现在写错就停，且错误指名道姓。

至于自激本身，真正起作用的是四层，前两层在配置里：

1. `match` 只订阅"需要我决策"的状态——编排者典型是 `to: [BLOCKED, FINISHED]`，自己派发产生的 `→ IN_PROGRESS` / `entity.created` 不命中；
2. 别配"订阅自己会写的事件类型 + `wake`"（`entity.created` / `entity.updated` 就是自激配方）；
3. `selfQuietSec` + 同 aggregate 的 `loopMaxHits` 把"自己把自己叫醒"截断成最多几次（记 `skipped:self` / `skipped:loop`）；
4. 整个会话的 `stormMaxDeliveries` 达到阈值就**暂停全部订阅并通知**，不自动恢复。

**局限如实写**：事件信封里没有 `actor.sessionId`（只有 `operator` 用户名），所以"是谁改的"判断不出来，以上都是**截断**不是识别。要精确拦截需基座产生侧补 sessionId。

```text
[ ] match 里没有 key / aggregateId
[ ] inject 里的每个 {{...}} 都在白名单里
[ ] coalesceSec / maxPerHour / loopWindowSec / loopMaxHits 是正整数（或省略）
[ ] selfQuietSec 是 ≥0 的整数（`0` 是有意的关闭，不是"更安静"）
[ ] 没有拼错的键（M2 会拒；M1 会静默忽略）
[ ] 知道 notify 不烧 token，但也没注入——需要模型动手就写 wake
[ ] 用校验器跑过：无 error、可用规则数 = 期望
```

**不要做的事**

- 不要在 `filter` 里写状态、`match` 里写 key/aggregateId——两处都直接拒。
- 不要指望订阅级未知键会报错（会被静默忽略）。
- 不要订阅自己会写的 `entity.created` / `entity.updated` 还配 `action: wake`。
- 不要用 `notify` 当"先试试"——M1 里它等于暂停。
- 不要在同一条 channel 上期待"改完 filter 还能收到改动前的事件"（重建连接从当前时刻起算）。
