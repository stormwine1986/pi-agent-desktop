# 工作台视图的配置指南

> 适用版本：工作台 0.10.0（桌面应用包 0.8.2）
> 最后核对：2026-11-08，实测环境 `entity-demo-system-evan` / `ws_entity_base`
> 相关实现：`lib/views/`、`app/api/views/route.ts`、`components/ViewsPanel.tsx`
> 相关需求条目：`SSR-000066`（VW-CFG 配置与校验）、`SSR-000067`（VW-RUN 求值、分页与降级）、`SSR-000087`（VW-NAV 组织与导航）、`SSR-000089`（VW-WATCH 观察与派发）、`SSR-000090`（VW-CLAIM 认领与判定）

本文只讲**怎么配**。DQL 语法本身看 `dql-query` 技能文档；派发的设计推演看 [view-watch.md](view-watch.md)（已归档，以需求条目为准）。

---

## 0. 先理解三件事

1. **一条视图 = 一次 `list` 工具调用的结果，摊成一张表。** 视图自己不做计算、不做过滤、不做聚合，它只是把配置里的 `dql` / `orderBy` / `pageSize` 原样交给 `list`。
2. **面板是只读的。** 唯一的写操作是顶部「新建」（在**当前视图**的 `server` + `workspace` 里建一条实体）。派发（`watch`）会在后台写状态迁移，那是另一回事，见第 10 节。
3. **一条配置坏，只影响它自己。** 其它视图照常求值，坏的那条在侧栏标红点、悬停看原因。

由此得到最重要的推论：**视图的能力上限 = DQL 的能力**。想看的东西写不进 DQL，就别硬塞进视图（第 6 节列了四条硬约束）。

## 1. 五分钟起步

文件：`<项目根>/.pi/views.yaml`

```yaml
views:
  - title: 待办任务
    server: entity-demo-system-evan
    workspace: ws_entity_base
    dql: "type = 'TASK' and state = 'DEFINED'"
    columns: [key, name, priority, owner]
    orderBy: modified_at
    order: desc
    pageSize: 20
```

打开面板的方式：

- 侧栏项目右键 →「打开待办视图」；
- 项目里存在 `views.yaml` 时，右侧面板**默认就落在待办页**（启动时用 `GET /api/views?probe=1` 探一次，只读文件、不跑查询）；
- 待办页在右侧面板里是一个 tab，标题「待办」，每个项目一个。

保存即生效：文件每次求值都重新读，**不需要重启**。点「刷新」立刻重读，否则等下一轮轮询（最多 60 秒）。

## 2. 文件放在哪、什么时候重读

按 cwd 依次查找，**用第一个存在的**：

```text
.pi/views.yaml      ← 标准位置
.pi/views.yml
views.yaml
views.yml
```

- 文件不存在不是错误：面板显示「尚未配置视图：在这个项目里创建 `<路径>`」。
- 文件读不进、YAML 解析失败、根节点不是对象 → 整块报错，没有视图可用（这是**文件级**错误）。
- 单条视图有问题 → 只有那一条标红（**条目级**错误），其余正常。

重读时机：

| 触发 | 效果 |
| :--- | :--- |
| 每 60 秒的轮询 | 只在窗口可见时轮询；页面隐藏时不跑 |
| 切回窗口 | 立刻求值一次 |
| 「刷新」按钮 | 立刻求值 |
| 助手在本应用里写入某个 server 的实体 | 立刻求值并直接应用（不提醒，因为改动就在眼前） |
| 保存 `views.yaml` | 下一次求值即生效 |
| 改 `mcp.json` | 下一次求值即生效（每次求值都重新解析 server 配置） |

轮询失败时旧数据保留，顶部标「可能不是最新（截至 HH:MM）」。

## 3. 字段速查

```yaml
groups:                     # 顶层，可选：声明组顺序与默认折叠
  - 目标管理
  - title: 质量问题
    collapsed: false

views:
  - title: 待办任务          # 必填
    server: entity-demo-system-evan
    workspace: ws_entity_base
    dql: "type = 'TASK' and state = 'DEFINED'"
    columns: [key, name, priority, owner]
    orderBy: modified_at     # 可选
    order: desc              # 可选，只在 orderBy 存在时生效
    pageSize: 20             # 可选，1–100
    notify: true             # 可选，默认 true
    group: 目标管理          # 可选，一个视图一个组
    watch:                   # 可选，见第 10 节
      project: ../my-service
      prompt: .pi/prompts/task.md
      claim: { from: DEFINED, to: IN_PROGRESS, manual: BLOCKED }
```

| 键 | 必填 | 类型 | 默认 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| `title` | ✅ | string | — | 视图名。非空；**大小写不敏感唯一**；侧栏宽 180px 左右，建议 ≤ 14 字 |
| `server` | ✅ | string | — | `mcp.json` 里的 server 名。**只支持 HTTP 端点**（有 `url`）；stdio（`command`）直接报错 |
| `workspace` | ✅ | string | — | 工作空间 id（如 `ws_entity_base`）。填错不会在解析时报错，是求值时 `list` 报错 |
| `dql` | ✅ | string | — | 单行 DQL，**必须自带 `type = '...'`**（第 6 节） |
| `columns` | ✅ | string[] | — | 非空数组。表头就显示写下的字符串，**没有别名/中文标题映射**，建议 3–5 列 |
| `orderBy` | ❌ | string | 不发排序参数 | 该类型已定义的字段名；`modified_at` 与 `modifiedAt` 都可用 |
| `order` | ❌ | `asc`/`desc` | `desc` | **只写 `order` 不写 `orderBy` 时静默无效** |
| `pageSize` | ❌ | int 1–100 | `50` | 每页行数（不是「最多显示多少行」，见第 7 节） |
| `notify` | ❌ | bool | `true` | 轮询发现新条目时是否在侧栏提示 `+N`；`false` 则静默更新 |
| `group` | ❌ | string | 未分组 | 归入哪个组；空串等于未分组；**只能是字符串，不是数组** |
| `watch` | ❌ | object | 无（只读视图） | 派发配置，见第 10 节 |

两条容易踩的：

- **未知键被静默忽略。** 把 `pageSize` 写成 `page_size`、`orderBy` 写成 `order_by`，不报错，只是悄悄用回默认值。键名**大小写敏感**，逐字核对。
- **`server` 接受 pi 的命名空间写法。** 配置里写 `entity-demo-system-evan` 或 `entity_demo_system_evan` 都能解析到同一条条目（pi 在工具名里把 `-` 写成 `_`），解析后一律用 `mcp.json` 里的拼写。

## 4. 写之前必须做的四步

视图的多数错误**不会报错**（列空白、空表、排序没生效），只能靠事前实测发现。顺序不要跳：

**① 确认 server 与 workspace**

```text
读 <项目>/.pi/mcp.json（优先）或全局 mcp.json → mcpServers 下取名字
确认该项是 url 型（http/https），不是 command 型
workspace 用 list_types / about_me 确认当前凭据可读
```

**② 查 schema，不要凭记忆**

```text
get_metadata('<类型>')
→ fields（字段名、类型、validValues、permissions）
→ lifecycle.validStates（该类型的合法状态）
→ traceability（可用的追溯关系与方向）
```

**③ 用 `list` 跑一遍完全相同的参数**

视图执行的就是这条调用，它过不了视图一定过不了：

```text
workspaceId = 配置里的 workspace
query       = 配置里的 dql
limit       = 配置里的 pageSize
offset      = 0
orderBy / order = 与配置一致（有 orderBy 才传 order）
includeTotal = true          ← 面板总会传，量一下总数
```

实测例（本仓库当前数据）：

```text
list(workspaceId="ws_entity_base", query="type = 'SSR'", orderBy="modified_at", order="desc", limit=3, includeTotal=true)
→ total=90, keys=[SSR-000067, SSR-000083, SSR-000087]
```

**④ 拿返回的 `item` 核对 `columns`**

列名不要从 `get_metadata` 抄字段表，而是从 `list` 实际返回的 `item` 里挑（第 5 节的映射规则）。逐列看一眼有没有值——常年为空的字段放进表就是一行空白。

## 5. 列名怎么映射到实体字段

表头 = 你写的字符串。单元格取值按这个顺序找，**第一个命中的就用**：

```text
对每个候选名：  1. 字面名（b）
               2. camelCase（created_by → createdBy）
               3. snake_case（createdBy → created_by）
每一轮都先查 item 顶层，再查 item.fields
```

实用结论：

- `created_by` ≡ `createdBy`，`created_at` ≡ `createdAt`，写哪个都行。
- **系统字段**来自顶层：`key` / `name` / `state` / `description` / `revision` / `createdBy` / `modifiedBy` / `modifiedAt`。
- **业务字段**来自 `fields`：`priority`、`owner`、`spec_compliance` 这类，顶层没有同名也能取到。
- **列名写错不报错，整列空白**——这是最常见的「视图看起来正常但没数据」。
- 对象/数组会被 JSON 字符串化；每列最宽 320px、单行截断，悬停看全文。`description` 这类长文本不要进列。
- 数字与布尔会转成字符串显示；`null` / `undefined` 显示为空。
- **第一列放 `key`。** 行内「带入会话」「打开实体」都靠实体自身的 `key`（不是靠 `columns`），不放 `key` 就没人可读的编号。

## 6. `dql` 在视图里的四条硬约束

1. **必须写 `type = '...'`。** 视图调 `list` 时不传 `entityType`（它只是 `orderBy` 的类型上下文，**不是过滤器**），类型过滤只能靠 DQL。漏了会混进别的类型，列大面积空白。
2. **状态值必须来自该类型的 `get_metadata().lifecycle.validStates`。** 不同类的合法状态不同（`TASK` 是 `DRAFT/DEFINED/IN_PROGRESS/BLOCKED/FINISHED/INVALID`，`SSR` 只有 `DRAFT/DEFINED/INVALID`）。
3. **关系谓词必须同时写 `type`**；`relation = '<id>'` 传的是**实体 id，不是 key**（传 key 静默 0 条）。
4. **不能写 `order by` / `limit` / `offset`**，排序分页走 `orderBy` / `order` / `pageSize`。

视图特有的两个没有：

- **没有变量替换。** `${user}`、`${ENV}` 不会被展开（`${VAR}` 只在 `mcp.json` 里有效）。要「我的」只能写死用户 id。
- **没有时间函数、没有聚合。** `now()`、「最近 7 天」、count / group by 都写不出来。最多用固定日期 + `orderBy: modified_at`。

### YAML 写法

推荐做法：整条 DQL 用双引号包住，内部字符串用单引号。

```yaml
dql: "type = 'TASK' and state = 'DEFINED'"
```

引号混用、或 DQL 里含 `#` / `: ` 时，用折叠块标量（换行会折叠成空格，DQL 仍然合法）：

```yaml
dql: >-
  type = 'TASK' and (state = 'DEFINED' or state = 'BLOCKED')
  and name contains '导出'
```

- 空格缩进，**不要 Tab**；UTF-8 编码，中文没问题。
- DQL 里出现 `: `（冒号+空格）或 `#` 而没加引号，会被 YAML 当成映射/注释截断。

## 7. 分页与总量

视图是**真的翻了页**，不是截断：

- 每条视图各自记住自己的 `offset`，求值时把已翻过的视图一起传给 `/api/views`（形如 `offsets={"0":50,"2":100}`，按在文件里的位置索引），没翻过的视图从第 1 页开始。
- 表头显示 `1–20 · 共 320 条`（`offset+1` – `offset+行数`，总数来自 `includeTotal`）。**总量比区间更重要**：一个悄悄停在 `pageSize` 的视图会被读成「就这么多」。
- 只有真的能翻时才出现箭头：左侧 `‹`（能回）与右侧 `›`（还有更多）。`hasNext` 有总数时是算术（`offset+count < total`），没总数时以「本页满页」为唯一证据。
- **越界自愈**：停在第 3 页时前面的条目被移出视图（比如状态变了），`offset` 会越界；面板会自动退到最后一个有内容的页，而不是显示空页——空页会被读成「视图空了」。
- **「数据已变化」**：只在「已在第 2 页及以后 + 总数与上一轮不同」时出现，翻页即清。第 1 页不提示，否则每轮都是噪音。
- `offset` 与「当前选中的是第几条视图」都只存在内存里，**不写进 `views.yaml`**，刷新页面后回到第一页。

因为每页是一次独立的 `list` 调用，**翻页期间的增删会如实反映**（不是对旧结果做内存切片）。

## 8. 提醒：`notify` 与 `+N`

- 轮询（`diff` 模式）拿回新结果后，按**新出现的 `key`** 计数：`+N` 出现在侧栏该视图行尾（替代平时的行数）。
- 有 `+N` 的视图**保留你正在看的旧内容**（不会突然换掉你读的表），其它视图直接更新。
- 点那条视图行 = 应用新结果并清掉 `+N`；点「刷新」同样清掉。
- `notify: false`：新条目**直接出现**，不提示。
- 计数是按当前页比较的：只看这一页的 key 有没有新增。

## 9. 分组（`group` / `groups`）

```yaml
groups:                 # 顶层，可选。声明顺序 = 导航里的组顺序
  - 目标管理
  - title: 质量问题
    collapsed: true     # 默认收起

views:
  - title: 待办任务
    server: entity-demo-system-evan
    workspace: ws_entity_base
    dql: "type = 'TASK' and state = 'DEFINED'"
    columns: [key, name, priority]
    group: 目标管理     # 视图级，可选
```

- **`group`**（视图级，字符串）：写组名即归入；**空串或不写 = 未分组**（空串不报错，方便你删组名时留下键）。
- **`groups`**（顶层，数组）：元素可以是组名字符串，或 `{ title, collapsed }`（`collapsed` 可省，默认 `false`）。`groups` 只能是数组，写成映射或单个字符串是**文件级**错误。
- **顺序**：`groups:` 声明顺序（只画真正有成员的组，空组不画）→ 未声明的组按首次出现 → **未分组视图恒在最后**。组内顺序 = `views:` 里的配置顺序，与 `orderBy` 无关。
- **一个视图只属一个组**（`group` 是字符串）；要出现在两处就再写一条视图（`title` 必须不同）。
- **组头**显示箭头、组名、以及两个状态点：蓝点 = 当前正在看的视图在这个组里（组折叠时也用得上），红点 = 组内有配置错误。悬停提示「组名（N 个视图）」。
- **折叠只影响呈现**：折叠的组仍然求值、仍然累计 `+N`；展开看到的是最新结果，不是折叠前的缓存。
- **折叠状态是本地偏好**（按项目存在客户端），不回写 `views.yaml`；没存过时用 `groups[].collapsed` 作初始值。
- **组名整串精确匹配**（首尾空格已 trim，大小写不同 = 不同组）；同名重复声明算同一个组，不报错。

## 10. 派发：`watch`

把视图变成**待处理队列**：视图里还有条目，就派**最老的那一条**给指定本地项目开一个会话去做。

一句话边界：**机制负责「认领」和「判定」，不负责业务。** 泵只写两个状态迁移（认领 / 待人工），业务字段（结论、方案）完全由执行项目自己写。

### 配置

```yaml
views:
  - title: 待开工任务
    server: entity-demo-system-evan
    workspace: ws_entity_base
    dql: "type = 'TASK' and state = 'DEFINED'"     # ← 必须恰好含一个 state = '<from>'
    columns: [key, name, priority, owner]
    orderBy: modified_at
    order: asc
    watch:
      project: ../my-service          # 执行项目目录；相对路径按 views.yaml 所在项目解析
      prompt: .pi/prompts/task.md     # 任务说明文件；同样按项目解析
      intervalSec: 90                 # 可省，默认 90
      timeoutMin: 120                 # 可省，默认 120
      enabled: true                   # 可省，默认 true
      claim:
        from: DEFINED                 # 待处理状态，必须与 DQL 里的 state 一致
        to: IN_PROGRESS               # 认领态：派发前写它，写成功才算派出
        manual: BLOCKED               # 待人工：没做完 / 超时，落在这里且不再自动派
```

| 键 | 默认 | 说明 |
| :--- | :--- | :--- |
| `watch.project` | 必填 | 执行项目目录。不存在 → 视图不派发并显示原因 |
| `watch.prompt` | 必填 | 任务说明文件。不存在 / 空文件 / 读不到 → 不派发 |
| `watch.intervalSec` | `90` | 该视图两轮之间的最短间隔（秒）。全局泵每 60 秒走一圈 |
| `watch.timeoutMin` | `120` | 认领超过这么久 → 移到 `manual`（视为卡住） |
| `watch.enabled` | `true` | `false` = 只读视图，不派发 |
| `watch.claim.from` | 必填 | 待处理状态。**必须等于 DQL 里那个 `state = '...'`** |
| `watch.claim.to` | 必填 | 认领状态。派发前写入 |
| `watch.claim.manual` | 必填 | 待人工状态，且**不能等于 `from`**（否则立刻被重新派发） |

**已移除的键会直接报错**（不是静默忽略）：`claim.back`（失败归还重试）、`maxFailures`（失败次数上限）——现在没有重试，失败第一次就进 `manual`。

### 校验：一条视图要过这五关才会派发

不通过就**完全不派发**，面板在该视图行上标**红点**、正文里写「派发未生效：<缺什么>」：

1. `watch.project` 是目录；
2. `watch.prompt` 存在、非空、可读；
3. DQL 里**恰好一个** `state = '<值>'`，且该值等于 `claim.from`（`state in (...)`、`state != ...`、两个 `state =` 都无法切出认领态 → 拒绝）；
4. `claim.from` / `to` / `manual` 都是该类型 `lifecycle.validStates` 里的状态；
5. 状态机里存在 `from → to` 与 `to → manual` 两条路由。

第 4、5 关需要 `get_metadata`，所以 DQL 里没写 `type = '...'` 时这两关**跳过**（其余照查）。本仓库示例（`TASK`）：

```text
validStates: DRAFT / DEFINED / IN_PROGRESS / BLOCKED / FINISHED / INVALID
routes: DRAFT→DEFINED, DEFINED→IN_PROGRESS, IN_PROGRESS→FINISHED,
        IN_PROGRESS→BLOCKED, BLOCKED→DEFINED, BLOCKED→FINISHED, BLOCKED→INVALID,
        DRAFT→INVALID, DEFINED→INVALID
→ from=DEFINED, to=IN_PROGRESS, manual=BLOCKED 三关全过
```

### 运行规则

- **服务端循环**，与面板是否打开、切到哪个 tab、窗口是否可见无关；应用不退出就派发。
- 全局最多 **2 个** watch 会话并发；**同一执行项目同时最多 1 个**（判定见下面「派发与并发」）。
- **派发前有两道闸门**（`SSR-000089` ④⑦，2026-11-09 收紧）：
  1. **项目有运行中会话** → 本轮不派发。判定源是**应用侧会话运行态**（运行列表 + 每个会话的 `cwd`），**不是泵自己的索引**；你手工恢复 / 续跑的会话同样计入。终端里的手工进程看不到，也不计入。
  2. **有 N 条停在 `claim.manual`** → 本轮不派发。判定就是把视图 DQL 里那句 `state = '<from>'` 换成 `'<manual>'` 再查一次（`limit: 1` + 总数）；命中即整条视图停派，一条卡住挡全部。
  两道闸门只影响**派发时机**：闸门关闭期间不认领、不丢条目，打开后下一轮照常从最老的一条继续。面板会把该视图标成**黄点**，正文写「本轮跳过：项目有运行中会话」/「本轮跳过：有 N 条待人工」。

**面板上的四种派发状态**（`SSR-000089` AC-11）：**绿点** = 配好了、本轮无待派；**黄点** = 本轮被闸门挡住（带原因）；**没有点** = 这条视图不派发（只读）；**红点** = 暂停了（`enabled: false`）或上面五关没过（带缺失项）。判据只有 `/api/views` 返回的 `watch` 对象，面板不另存一份「是否配了派发」。所以「这条视图没有待处理」和「这条视图的派发关了」在面板上不是同一张脸。
- **跳过原因要看得见**：闸门关闭时面板在视图上显示「本轮跳过：项目有运行中会话」/「本轮跳过：有 N 条待人工」，不会表现为“没有待处理”。
- 多进程（dev server + 桌面应用同时开）靠文件租约互斥：**只有一个进程在派发**，不会认领两次。
- **派发顺序**：同一视图内按 `modified_at` 升序，即**最老的先做**；一轮最多派一条。
- **如何判「新的」**：不判。视图就是待处理队列，有就做。
- **怎么防重复派**：先写认领态，写成功才开会话；后到者拿到 `CONCURRENT_WRITE_CONFLICT` 就跳过。占用是实体上的共享事实，跨机器成立。
- **完成怎么判**：会话结束那一刻再读一次实体——**还是认领态 = 没做完**（进 `manual`，不重试）；被改成别的状态 = 执行项目已经处理，泵不再插话。
- **为什么不重试**：泵的判据分不出「活没干」和「干了没记账」，第二次尝试学不到新东西。决定下一步是人的事。
- **会话标题**：`视图名 · KEY`；同一实体再次被派发（只有人把它从 `manual` 挪回队列才可能）显示 `（第 N 次）`，N = 该实体历次进入认领态的计数。

### 派发与并发

「同一执行项目同时最多 1 个」按**应用内该目录有没有运行中的会话**判定，判定源是应用自己的会话运行态（运行列表 + 各会话的 `cwd`），不是泵的私有索引：

- 你在该项目里手工起一个会话、或者**续跑一条已经结束的人工会话**，同样会让该项目进入「有运行中会话」，本轮不派发；会话结束后下一轮自动恢复。面板会显示「本轮跳过：项目有运行中会话」。
- **终端里的手工进程看不到**（有意为之）：在终端里 `npm run dev` 之类不改变应用侧会话运行态，不会挡住派发。
- 不同项目互不影响：一个项目被挡住，别的项目照常派。
- 待人工闸门是**按视图**的：一条视图只要还有一条实体停在 `claim.manual`，整条视图停派，直到人把它移回待处理。
- 泵**不杀会话、不检查工作区、不做协调**（它只写认领与待人工两次状态迁移）。同一个工作树被两边同时改、改冲突、构建产物互相覆盖，后果由执行项目自己承担。

需要暂停派发时，唯一的手段是**把该视图的 `watch.enabled` 改成 `false`**：下一轮生效，已经在跑的会话不会被杀；处理完再改回 `true`。一期不做面板开关，`enabled` 就是唯一开关。

由此有一条人工纪律：**派发期间不要在同一项目里手工续会话**。确实要续跑时，先把对应视图 `enabled: false` 暂停，续跑结束后再恢复；否则请换一个项目、或者等这一轮跑完再动手。

### prompt 占位符

模板里支持 `{{name}}` 替换，未知占位符**原样保留**（这样拼错能看见）：

| 占位符 | 值 |
| :--- | :--- |
| `{{key}}` | 实体编号 |
| `{{type}}` | 实体类型 |
| `{{workspace}}` | 空间 id |
| `{{state}}` | `claim.from`（派发时的待处理状态） |
| `{{fields}}` | 实体的字段值，一行一个 `name: value` |
| `{{runCwd}}` | 执行项目目录 |

### 落地建议

先只读把视图跑通（第 4 节四步），确认表里就是你要处理的那批实体，再**复制**一份加 `watch`。别在一条还没验证过的 DQL 上直接开派发——它会让会话替你跑真正的工作。

## 11. 行内交互

| 操作 | 行为 |
| :--- | :--- |
| 行首「带入会话」按钮 | 把该行的实体（`server` + `workspace` + `key` + `name` + `state`）交给对话输入框，接着就能围绕它提问 |

这三件事都依赖实体自身返回了 `key`，与 `columns` 配置无关；但表里不放 `key` 列就没人能点。

## 12. 错误对照表

### 文件级（整个面板不可用）

| 提示 | 原因 |
| :--- | :--- |
| `读取失败：...` | 文件权限 / 编码问题 |
| `YAML 解析失败：...` | 缩进、Tab、引号、括号；按提示行列号改 |
| `根节点必须是对象，形如 views: [...]` | 顶层不是映射，常见于整个文件写成了数组 |
| `缺少 views 数组（views: [...]）` | 没有 `views` 键或拼错 |
| `groups 必须是数组（可写组名或 { title, collapsed }）` | `groups:` 写成了映射或单个字符串 |

### 条目级（只坏这一条，侧栏标红点）

| 提示 | 修法 |
| :--- | :--- |
| `这一项不是对象（应为 { title, server, workspace, dql, columns }）` | 列表项少了缩进，变成字符串 |
| `缺少 title` / `缺少 server（mcp.json 里的名字）` / `缺少 workspace` / `缺少 dql` | 补齐；空串也算缺 |
| `columns 必须是非空数组` | 写成 `columns: [key, name, state]` |
| `order 只能是 asc 或 desc（写的是 "..."）` | 只接受这两个值（大小写不敏感） |
| `pageSize 必须是 1–100 的整数（写的是 "..."）` | 超上限不截断，直接报错 |
| `notify 只能是 true 或 false（写的是 "..."）` | 不要写 `yes` / `no` |
| `group 只能是字符串（写的是 ...）` | 一个视图一个组；数组 / 对象都报错 |
| `title 重复："..."` | 标题大小写不敏感去重，改名 |
| `groups 第 N 项 ...`（空串 / 缺 title / 非对象 / collapsed 非布尔） | 按提示改那一项 |
| `watch 必须是对象（含 project / prompt / claim）` | `watch:` 下写成了字符串 |
| `缺少 watch.project` / `缺少 watch.prompt` / `缺少 watch.claim` | 补齐 |
| `watch.claim.back 已移除...` / `watch.maxFailures 已移除...` | 删掉这两个键 |
| `watch.intervalSec 必须是正整数` / `watch.timeoutMin 必须是正整数` | 写秒 / 分钟的整数 |

### server 解析

| 提示 | 修法 |
| :--- | :--- |
| `mcp.json 里没有名为 "x" 的 server（已配置：...）` | 用回显里的名字；项目与全局两处配置合并后生效 |
| `server "x" 是 stdio 类型（command），本功能只支持 HTTP 端点` | 视图只能连 HTTP MCP |
| `server "x" 没有 url` / `url 必须是 http(s)` | 补 `url` |
| `环境变量 XXX 没有设置` | `url` / `headers` 里用了 `${XXX}`，而该变量没设 |
| `配置值是 !command，本功能不执行命令` | 视图不执行命令 |

### 执行级（求值时才发现，报在正文里，附 `DQL：<你的表达式>`）

| 现象 | 原因 |
| :--- | :--- |
| 正文显示 DQL 错误 + `DQL：...` | DQL 写错或字段不存在 —— 先改 DQL，不是数据问题 |
| 空表：「这条查询没有匹配的实体」 | 查询本身没错，只是没命中 |
| 某一列整列空白 | 列名在该实体的顶层/`fields` 里都不存在；或该字段全空 |
| 排序没生效 | 只写了 `order` 没写 `orderBy`，或 `orderBy` 字段不在该类型上（`list` 会报错） |
| 「派发未生效：...」（红点） | 第 10 节五关之一没过，或该视图被 `enabled: false` 暂停 |

## 13. 常用配方

> 字段与状态值必须按 `get_metadata` 复核；下面用本仓库实测过的类型（`TASK` / `SSR` / `Defect`）。

```yaml
groups:
  - 我的队列
  - title: 质量

views:
  # 1. 待办队列：最老的在前，顺手派发出去
  - title: 待开工任务
    server: entity-demo-system-evan
    workspace: ws_entity_base
    dql: "type = 'TASK' and state = 'DEFINED'"
    columns: [key, name, priority, owner]
    orderBy: modified_at
    order: asc
    pageSize: 20
    group: 我的队列
    watch:
      project: ../my-service
      prompt: .pi/prompts/task.md
      claim: { from: DEFINED, to: IN_PROGRESS, manual: BLOCKED }

  # 2. 多状态 OR：待人工 + 被阻塞，最近改动的在前
  - title: 卡住的活
    server: entity-demo-system-evan
    workspace: ws_entity_base
    dql: "type = 'TASK' and (state = 'BLOCKED' or state = 'IN_PROGRESS')"
    columns: [key, name, priority, modified_at]
    orderBy: modified_at
    order: desc
    pageSize: 30
    group: 我的队列

  # 3. 数据质量巡检：还没评估的子系统需求
  - title: 未评估SSR
    server: entity-demo-system-evan
    workspace: ws_entity_base
    dql: "type = 'SSR' and spec_compliance is empty"
    columns: [key, name, state, owner]
    orderBy: modified_at
    order: desc
    group: 质量

  # 4. 未关闭的缺陷
  - title: 未关闭缺陷
    server: entity-demo-system-evan
    workspace: ws_entity_base
    dql: "type = 'Defect' and state not in ['RESOLVED','INVALID']"
    columns: [key, name, state, priority]
    orderBy: modified_at
    order: desc
    group: 质量

  # 5. 已实现但只完成一半的需求：最需要人盯的一批
  - title: 部分实现
    server: entity-demo-system-evan
    workspace: ws_entity_base
    dql: "type = 'SSR' and spec_compliance = '部分实现'"
    columns: [key, name, owner, modified_at]
    orderBy: modified_at
    order: desc
    pageSize: 20
    group: 质量
```

> **数据现状提示（2026-11-08）**：演示环境 `ws_entity_base` 里 `TASK` 全部是 `FINISHED`、
> `Defect` 全部是 `RESOLVED` / `INVALID`，所以配方 1/2/4 现在会显示「这条查询没有匹配的实体」。
> 这是数据状态，不是配置错——把状态换成实际存在的那批再调。配方 3（2 条）、5（10 条）当下有数据。

**`is empty` 的陷阱**：如果该字段全库从未被写过，`is empty` 会命中该类型的**全部**记录（看起来像筛选生效了，其实什么都没筛）。用之前先跑一次 `is empty` 和 `is not empty`，确认两边条数互补。

**关系谓词**要配 `type`、且传实体 id：

```yaml
    # 没有任何上游的实体（断链巡检）
    dql: "type = 'SSR' and upstream is empty"
```

## 14. 交付前自检

```text
[ ] 文件在 .pi/views.yaml（或已存在的那个候选路径）
[ ] 顶层是 views: [...]，空格缩进
[ ] 每条都有 title / server / workspace / dql / columns
[ ] title 互不重复（忽略大小写），足够短
[ ] server 是 mcp.json 里的 HTTP 条目；workspace 可读
[ ] dql 里写了 type = '...'，状态值来自 get_metadata
[ ] dql 里没有 order by / limit / 变量 / 时间函数 / 聚合
[ ] orderBy 与 order 成对；orderBy 是实测合法的字段
[ ] pageSize 是 1–100 的整数
[ ] 每个列名都在 list 返回的 item（顶层或 fields）里真实存在，且不是长文本
[ ] 第一列是 key
[ ] 每条都用 list 跑过同样参数，命中数符合预期
[ ] 保存后点「刷新」：侧栏无红点，各列有值，表头「共 N 条」对得上
[ ] 开了 watch 的：project 是目录、prompt 非空、claim 三态合法且路由存在、
    DQL 里恰好一个 state = from
```

**不要做的事**

- 不要把 `description` 这类长文本塞进列；不要指望列有中文别名。
- 不要写 schema 外的键（会被静默忽略，你还以为生效了）。
- 不要用 stdio server；不要在 `dql` 里做排序分页。
- 不要把 `group` 写成数组；不要指望按 DQL 内容自动聚类分组，分组只能手写声明。
- 不要在没验证过的 DQL 上直接开 `watch`。
