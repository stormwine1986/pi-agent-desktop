本目录记录**本仓库自己做了取舍的事**：现状、为什么这样、什么时候该改回去。不是缺陷台账（缺陷在演示系统的 `Defect` 里），
是给下次翻阅的人省一次排查。

## 2026-11-09 · MCP 入参预校验把 `anyOf` 只报一支（DEFECT-000081，已打依赖补丁）

**一句话**：工具调用的入参在本地预校验失败时，`anyOf` 只报「最后/最深失败的那一支」，把另一条合法路径整段隐去。
改在 `@earendil-works/pi-schema` 的 `walkUnion`，以**本仓库补丁**的形式落地（上游没有修复版本）。

### 现象（同一 API key、同一 args，两侧文案不同）

`list` 的 schema 是 `required: [workspaceId]` + `anyOf: [{required:[query]}, {required:[branchId]}]`，只传 `{workspaceId, limit}`：

| 位置 | 文案 |
| --- | --- |
| 服务端 `10.8.0.125`（正确） | `-32602 Missing required argument for tool 'list': provide one of [query \| branchId].`，`data.argument=query, reason=missing_any_of` |
| 调用侧（改前） | `Validation failed for tool "mcp__entity_base__list":` `- branchId: missing` ← `query` 不见了 |
| 调用侧（改后） | `- query: missing` / `- branchId: missing` |

`link` / `unlink` 同型：`{sourceId, linkType}` 缺目标时，改前只报 `targetIds`，`targetId` 被隐去。

危害不是文案洁癖：会被读成「这个空间必须先建分支才能查 DQL」，而 `ws_entity_base` **0 分支**、主干 DQL 完全可用。
依据 `SSR-000033`（错误必须携带可操作信息）、`SSR-000019`（DAT-API 错误码）。

### 根因（不在本仓库，也不在 entity-base）

- 判定处：`node_modules/@earendil-works/pi-schema/dist/explain.js` 的 `walkUnion` —— 全部失败时只挑
  「声明属性最多的分支，其次首个错误最深的分支」输出（`let best; …`）。
- 唯一调用点：`node_modules/@earendil-works/pi-ai/dist/utils/validation.js` 的 `validateToolArguments`
  —— pi 的**全部**工具入参都走这里，MCP 工具不例外。
- MCP 工具的 `parameters` 是服务端 `inputSchema` 原样透传
  （`node_modules/@earendil-works/pi-coding-agent/dist/extensions/mcp/tools.js` 的 `toParameters`），
  `anyOf` 一路无损到校验器。
- entity-base 一侧（`src/domain/tools/dynamic-tool-registry.ts`）文案本来就是对的，**不要动服务端**。

### 为什么是「本仓库打补丁」这个例外

`AGENTS.md` 的站位是「SDK 归上游」，正常情况下不该改依赖。这里例外，理由是三条同时成立：

1. npm 上 `@earendil-works/pi-schema` **只有 1.5.0**，没有已修复版本，等不到解；
2. 桌面版把仓库的 `node_modules` 打进 `src-tauri/resources/server`（`npm run desktop:prepare`），
   所以仓库级补丁能真的到达用户，而不是只在这台机器上；
3. 缺陷在**调用侧文案**，不碰服务端文案、不碰工具 schema、不碰业务数据 —— 与禁令不冲突。

**代价要知道**：这是一处对上游包 `dist` 的改写，升级 pi-schema 时可能失效（见下）。

### 补丁是什么

- `scripts/patch-pi-schema-union.mjs`：把 `walkUnion` 的「挑一支」换成「按分支顺序把每条不同错误都报出来」；
  带标签联合体（tag 命中/不命中）、「匹配多于一支」等既有分支原样保留。
  **只改错误文案，不改判定**：`ok` / 拒绝结论与改前完全一致。
- `package.json` 的 `postinstall` 末尾追加它 —— `npm ci` / 全新安装后自动重打，幂等。
- `scripts/pi-schema-union.test.mjs`：断言安装里的 pi-schema 已打补丁，并覆盖
  `list` / `link` 两条路径齐全、合法入参零误拒、带标签联合体文案不变。
- 锚点找不到（例如 pi-schema 升级改了 `walkUnion`）时 **postinstall 直接报错**，不静默跳过：
  静默跳过会让文案悄悄退回旧行为，正是这个缺陷的原始症状。

### 遍历与验证（2026-11-09 实测）

遍历 5 个端点的 `tools/list`（共 126 个工具条目），`anyOf` 只出现在 `list` / `link` / `unlink`，`oneOf` 为 0：

| 端点 | 工具数 | anyOf | oneOf | 含联合体的工具 |
| --- | --- | --- | --- | --- |
| entity-base（`10.8.0.125:3100`） | 22 | 3 | 0 | list, link, unlink |
| manhu-admin / z100100 / l100101 / w100102（`localhost:3000`） | 33 / 27 / 22 / 22 | 各 3 | 0 | list, link, unlink |

用各端点**真实 schema** + pi-ai 同款校验选项，改后 15 个实例全部两条路径齐全；
7 组合法入参（`query:""`、只给 `targetId`、只给 `targetIds` 等）改前改后都通过、结果一致；
15 个实例 × 2 组入参共 30 组判定未变；带标签联合体文案未变。

自检：

```bash
node scripts/patch-pi-schema-union.mjs --check   # 安装里有没有这个补丁
node --test scripts/pi-schema-union.test.mjs     # 文案与零误拒
```

### 边界（这次没做的）

- **只影响本仓库与它打出来的桌面版**。系统里已装好的 App 有自己的一份运行时，重打包前仍是旧文案。
  打过补丁后要重新 `npm run desktop:prepare`，`dist` 才会被复制进 `src-tauri/resources/server`。
- 只改了 `dist/explain.js`，没动 `explain.js.map`：源映射与 dist 现在有偏差，仅影响调试栈。
- 不改服务端错误码与文案、不改工具 schema 本身、不动业务数据。
- entity-base 的 `dynamic-tool-registry.spec.ts` 里关于 `anyOf` 的断言是**服务端**行为，与本补丁无关，别混。

### 本次打包（2026-11-09，含本补丁）

本地（非发布）打包与 CI 的 `desktop-test-build` 一致：关掉更新包签名、带一个可辨识的版本号，
否则 `createUpdaterArtifacts: true` 要签名私钥：

```bash
npm run desktop:prepare
npx tauri build --target x86_64-pc-windows-msvc --bundles nsis \
  --config '{"version":"0.8.2-local","bundle":{"createUpdaterArtifacts":false}}'
```

产物：`src-tauri/target/x86_64-pc-windows-msvc/release/bundle/nsis/Entity Assistant_0.8.2-local_x64-setup.exe`。

已核验：`src-tauri/resources/server/.../pi-schema/dist/explain.js` 带补丁标记，安装包内的同名文件也是；
`npm run desktop:verify` 通过（打包后的 Code mode 沙箱 + 终端）；用**包内** `node.exe` 调**包内** pi-ai 的
`validateToolArguments` + 真实 `list` schema，得 `- query: missing` + `- branchId: missing`，合法调用照常通过。

### 什么时候删掉它

上游 `@earendil-works/pi-schema` 在 `walkUnion` 里全报（或提供开关）之后：

1. 删 `scripts/patch-pi-schema-union.mjs`、`scripts/pi-schema-union.test.mjs`；
2. 把 `package.json` 的 `postinstall` 还原成 `node bin/prepare-terminal.js`；
3. 升级 pi-schema，`node --test scripts/pi-schema-union.test.mjs` 若已不存在，
   直接按本节上面「现象」表里的三条路径手测一遍（`list` 缺 query/branchId、`link` 缺目标）。

在那之前：**别把这个补丁当成 SDK 行为**，也不要据此再写第二套错误文案逻辑。

## 2026-11-12 · SSYS-000005 / SSR-000095：覆盖安装与退出清理里无法在本机验证的 5 条

**一句话**：产品口径（2026-11-12）定「不具备验证条件的 AC 从 SSR 移除，计入子系统的已知问题」——
`SSR-000095` 把原 AC-3、AC-4、AC-5、AC-7、AC-9 以及 AC-6 的两条失败路径子项移出验收标准，
原文与「为什么现在验不了 / 现有替代证据 / 什么条件下才能验」记在这里；编号沿用原 AC 号，
台账里现在剩下 AC-1 / 2 / 6（可验证的一半）/ 8 / 10 / 11，AC 头部写明了去向。

### 公共前提（下面四条共用）

产品 2026-11-10 写死：**无测试机、无 VM / Windows Sandbox、不建临时 Windows 账户**。
本机唯一的一份应用在 `%LOCALAPPDATA%\Entity Assistant`，它同时承载着执行任务的那个会话
（壳 `pi-agent-desktop.exe` + 子进程 `resources\node\node.exe`），所以既不能在它上面跑覆盖安装，
也不能把它卸掉。AC-3 / AC-5 / AC-9 都要**在用户已装目录上**跑安装器或卸载器，全部卡在这条上。

### 原 AC-3 · `/S` 静默自愈

> AC-3 静默安装自愈：/S 安装时存在残留服务端 → 自行结束并安装成功，退出码 0；不得因占用失败。

| 为什么现在验不了 | 现有替代证据 | 什么条件下才能验 |
| --- | --- | --- |
| `/S` 必须跑在真实安装目录上才叫「自愈」；在一次性目录里跑，装的是一个空目录，验不到「先要结束残留服务端」。本机安装目录承载当前会话，不能动。 | ① 机制：`EA_ReleaseBundledRuntime`（`src-tauri/installer-hooks.nsh`）先 `CheckIfAppIsRunning`，再按完整路径 `RestartManager_ShutdownFile`，`Sleep 500` 后 `FileOpen … a` 实测可写；② 静默分支已可执行验证：`scripts/installer-silent-branch.test.mjs`（`/S` 不弹 `MessageBox`）+ `scripts/installer-release-record.test.mjs` 把钩子展开成一个探针安装器，对 fixture 文件实跑：占用者被结束 → 记录 `strategy=shutdown-and-overwrite code=0`；锁不住时记录 `strategy=abort-locked code=1603`；③ `/S` 失败现在有确定退出码（`SetErrorLevel 1603`）。**未验**：真实安装目录上的 `/S` 覆盖安装、退出码 0、装完 payload 真的换了。 | 一台一次性 Windows（VM / Sandbox / 一次性账户 + 一次性 `INSTDIR`）：先造一个普通同会话的残留服务端 → `Start-Process <setup> -ArgumentList "/S" -Wait -PassThru` → 期望 `ExitCode 0`、`desktop.log` 里出现 `installer: … strategy=shutdown-and-overwrite code=0`、`resources\server\.next-desktop\BUILD_ID` 与 `component-versions.json` 的 `buildId` 一起变。 |

### 原 AC-4 · 真 `taskkill /F` 壳 E2E

> AC-4 强杀不留孤儿：taskkill /F 结束主程序后 ≤2s 内 resources\node\node.exe 退出；进程表里不再有该路径的 node.exe。

| 为什么现在验不了 | 现有替代证据 | 什么条件下才能验 |
| --- | --- | --- |
| **结构上做不到**，不是权限或资源问题：`tauri-plugin-single-instance` 是第一个注册的插件（`src-tauri/src/lib.rs`，`cfg(windows)`），互斥体名只取 `app.config().identifier`（`com.abcwyc.pi-agent-sim`），不含版本也不含安装路径（`src-tauri/Cargo.toml` 是裸 `"2"`，没开 `semver` feature）。`/D` 装到一次性目录、复制出来的便携目录、`tauri dev` 起的第二份壳，启动都拿到 `ERROR_ALREADY_EXISTS` → 通知主实例 → 自己退出。本机不存在「第二个壳」可杀，唯一能杀的壳就是承载本会话的那个（它的 kill-on-close Job 会带走服务端，等于自己拆执行环境）。见 `TASK-000098` 备选 B 的现场实证。 | 四层：① `src-tauri/src/shell/job.rs` 单测 `closing_the_job_kills_the_server_it_owns`；② 实机 `IsProcessInJob`=True、Job 的 `LimitFlags=0x2000`（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）；③ 代理实验：对 Job 句柄唯一持有者直接 `TerminateProcess`（模拟壳崩溃）→ 成员 100 ms 内消失；④ 静态兜底：`attach` 失败时 `desktop.log` 记 `could not attach the server to a kill-on-close Job Object`，改由 `server-launcher.cjs` 的 1 s 看门狗。本轮另补了正常退出的记录行（`cleanup: strategy=taskkill-tree pid=… job=kill-on-close restart-manager=not-used-by-shell code=…`），但**崩溃那一支仍然只能等一次性环境**。 | 一台不承载会话的 Windows：启动应用 → `Stop-Process -Id <壳 PID> -Force`（不要 `/T`，让 Job 自己收拾）→ 1–2 s 后 `Get-CimInstance Win32_Process -Filter "Name='node.exe'"` 过滤 `ExecutablePath -like "<INSTDIR>\resources\node\node.exe"` 应为空；同时确认 `desktop.log` 没有 `could not attach the server…`。 |
| 附：崩溃时壳已经死了，`desktop.log` 里不会有它自己的记录——那一半由 `server.log` 的 `desktop shell (pid …) is gone; server exiting`（launcher 看门狗）补，**不要**把「壳没留下记录」当成「没取证」。 | | |

### 原 AC-5 · 崩溃后直接重试安装

> AC-5 异常退出后可重试：崩溃/强杀后不手工清理进程，直接重试安装即可成功（本次"点重试仍失败"必须消失）。

| 为什么现在验不了 | 现有替代证据 | 什么条件下才能验 |
| --- | --- | --- |
| 它是 AC-4 的下游判据：要先能真崩一次、且崩完留下（或没留下）孤儿，再原样重跑安装器。崩这一步本机做不到（见 AC-4），重装这一步又要动已装目录。 | 只到机制：AC-4 的四层证据说明「壳死 → Job 关 → 服务端跟着死」，所以「重试时 node.exe 不再被占」在机制上成立；安装器的占用检测也不再只看主程序（AC-1 已通过）。**未验**：崩溃后第一次重试安装的实际结果。 | 同 AC-4 的环境，加一步：崩溃后**不清理任何进程**，直接再跑一次安装器；期望安装成功、`desktop.log` 里 `installer:` 记录 `pids=none` 或列出被结束的残留 PID。 |

### 原 AC-7 · 延迟替换（`MoveFileEx`）

> AC-7 延迟替换：走 MoveFileEx 类延迟替换时，本次安装返回成功，重启后实际生效的是新二进制，且版本自证与包清单一致。

| 为什么现在验不了 | 现有替代证据 | 什么条件下才能验 |
| --- | --- | --- |
| 这不是「没条件验」，是**不打算做**：现行实现选了另一支（「释放失败即拦下 + 启动时拒绝混装」），代码里没有延迟替换，一条都没有——所以没有可验的对象。合同④允许二选一（回滚 / 延迟替换），本实现三样都不走，用「拒绝启动」兜住混装。 | 替代的那一支已有证据：`scripts/node-runtime-mismatch.test.mjs`（payload 声明的 node ≠ 运行中 `process.version` → `refusing to start … run the installer again`、退出码 1、不加载 server；无 stamp 的老安装照常启动）；`npm run verify:install`（见 AC-8）把清单、`node-runtime.json`、`node.exe` 哈希三者对齐。 | 只有当产品决定改成延迟替换时才需要：实现 `MoveFileEx(…, MOVEFILE_DELAY_UNTIL_REBOOT)` 分支 → 一次性 Windows 上装一次 → 重启 → `verify:install` 通过且 `BUILD_ID`/`gitCommit` 是新的。在那之前这条应当**保持移出**，不要按「没条件验」重新排期。 |

### 原 AC-9 · 卸载同口径

> AC-9 卸载同口径：服务端在跑时执行卸载，不弹文件锁；卸载完成后不留 resources\node\node.exe。

| 为什么现在验不了 | 现有替代证据 | 什么条件下才能验 |
| --- | --- | --- |
| 卸载跑的是安装目录里的 `uninstall.exe`，会把承载本会话的应用本体移走（`resources\node\node.exe` 正是服务端自己），本机不能做。 | 代码与安装同源：`NSIS_HOOK_PREUNINSTALL` 复用同一个宏（`src-tauri/installer-hooks.nsh`），生成的 `installer.nsi` 里钩子在 `CheckIfAppIsRunning` 与首次 `Delete` 之前（卸载段同序）；本轮给这个宏加了 `action=uninstall` 标注与同一条记录行，所以真机一跑就能从 `desktop.log` 分出安装/卸载。**未验**：真实卸载不报文件锁、卸完不留 `node.exe`。 | 一次性 Windows / 一次性账户：服务端在跑时执行 `"<INSTDIR>\uninstall.exe"`（交互或 `/S`）→ 无文件锁弹窗；结束后 `Test-Path "<INSTDIR>\resources\node\node.exe"` 为 False；`desktop.log` 出现 `installer: action=uninstall … strategy=shutdown-and-overwrite`。 |

### 原 AC-6 的两条失败路径子项

> AC-6 失败不混装：中途失败或用户选「忽略」后，若发生跳过，则最终安装不得留下可运行的「新 payload + 旧 node」（或反向）组合——要么回滚，要么启动时版本校验拒绝并给出可操作提示。

台账里 AC-6 只保留**可验证的一半**（版本不一致时拒绝启动、退出码非 0）。被移出的两条：

| 子项 | 为什么现在验不了 | 现有替代证据 | 什么条件下才能验 |
| --- | --- | --- | --- |
| 「Abort 之前一个字节都没写」 | 要在真实安装目录上制造一次失败，再逐文件比对装前/装后快照；本机不能装。 | ① 代码顺序：钩子在 `RMDir /r node_modules` 与首次 `File` 写入之前（生成的 `installer.nsi` 里 634 行钩子、637 行 `CheckIfAppIsRunning`、643 起写入）；② 本轮把钩子展开成探针安装器实跑（`scripts/installer-release-record.test.mjs`）：`FileOpen` 失败 → 记录 `strategy=abort-locked code=1603` → `Abort`，探针不写目标目录；③ `TASK-000098` 备选 A 评估过 ACL 拒绝写注入（`icacls … /deny …:(WD,AD)`），本轮用同一手法在 fixture 上跑通了失败分支。**未验**：真实安装目录的装前/装后快照无差异。 | 一次性 Windows + 一次性 `INSTDIR`：装前 `Get-ChildItem -Recurse -File → pre.csv` + 三个哈希 → 用 ACL 或高完整性占用者制造失败 → 点「确定」/`/S` 走 Abort → 装后 `post.csv` 用 `Compare-Object` 比对，期望无差异（含 `node_modules`、`route-cache` 哨兵文件）。 |
| 「用户点忽略后逐文件跳过」 | 需要钩子先通过、随后 `File` 写 `node.exe` 时才失败，再在弹窗上点「忽略」；ACL 注入在钩子处就拦下了，到不了这一步。本机也不能装。 | 只有相邻的一半：启动时的版本校验拒绝（`scripts/node-runtime-mismatch.test.mjs`）。也就是说「跳过之后到底会不会混装」目前**没有**任何实测，别把那一半当这一半。 | 一次性 Windows + 一个 RM 关不掉的占用者（管理员进程 / 另一个登录会话）让钩子恰好通过而在写 `node.exe` 时失败 → 点「忽略」→ 装完启动：期望 `refusing to start … run the installer again`，且 `verify:install` 报 `node-sha256` 或 `buildId` 不一致（退出码非 0）。 |

### 什么时候该改回去

一旦有了一台一次性 Windows（VM / Windows Sandbox，或一个可随意装/卸的账户与目录），
